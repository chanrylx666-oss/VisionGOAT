# 编辑器性能与实时预览（2026-10-21）

本轮优化作用于 WPF 编辑器的配方执行与图像显示，不改变算子参数、拟合精度或图像分辨率。继续使用 Visual Studio 源码开发和普通 Debug 构建，没有制作独立发布程序。

## 已实现

- `EditorExecutionCache` 只保留最近一个编译配方和会话。未修改的配方再次执行时复用；参数、ROI、模板、连接或公开输出改变后重建。每次仍传入新的图像、运行输入、变量和预览请求，不缓存运行结果。校验失败、取消或异常不会回退到旧结果。
- 配方封装、校验、落盘、加载和运行接受移到后台任务，避免首次准备配方阻塞界面。缓存目录有界，替换或退出时释放；正在执行时拒绝重复请求，关闭时等待执行结束后释放。
- 相机预览直接从相机拥有的只读像素创建冻结位图，省去预览专用的 `ToVisionFrame → CopyPixels` 往返。主图和相机管理窗共享同一位图。
- 主窗口每 100 ms 拉取最新帧，最多约 10 次/秒；没有逐帧排队等待显示。这个上限只控制显示刷新，不改变相机采集帧率。相同尺寸的新帧保留缩放与拖动位置。
- 一次执行中移除重复的原图和结果图显示调用，减少大图重复复制。日志分别记录取图、配方准备、SDK 执行、结果显示准备及总耗时；显示准备不包含后续 GPU 合成和屏幕刷新。

## 操作

选择“全局相机”并连接、开始预览后，主窗口“图像与中间结果”区域显示实时画面。也可在图像下拉框中选择“实时画面”。关闭相机管理窗后，主图仍继续预览。

点击执行、取图用于教学或编辑 ROI 时，主图切换到固定图像。检测结果与教学 ROI 不会被新预览帧覆盖。需要观察实时图时，再选择“实时画面”。停流、断开或故障会清除正在显示的实时图，并显示相应状态；固定的检测／教学结果仍属于原来的输入帧。

## 并发与多进程

当前采集、WPF 显示和算法计算分别执行，采集槽只保留最新一帧。同一流程中的节点按依赖顺序执行；原生层支持多个独立会话并发，并限制活动运行数量，OpenCV 当前使用两条计算线程。

本轮没有加入多进程。它不能省掉本次发现的重复配方加载和图像往返，传递一张 5120×5120 灰度图还需要处理约 25 MiB 数据的共享内存、同步和生命周期。后续若要提高多相机或批量检测吞吐，可先使用有界的独立会话池，并分别测量单帧延迟、吞吐、内存及 CPU；不要让多个进程同时控制同一相机。

## 复测

最终正常 VS Debug 输出的本机复测（12 个逻辑处理器、.NET 10.0.12、5120×5120 Gray8 合成图、各路径预热 3 次后交替测量 30 次）：

| 测量范围 | 原路径中位数 | 优化后中位数 |
| --- | ---: | ---: |
| 预览位图准备 | 46.23 ms | 10.90 ms |
| 外部图像 → 灰度流程，SDK 端到端 | 10.28 ms | 3.08 ms |
| 全图 Blob 流程的配方准备阶段 | 12.69 ms | 0.001 ms |

预览位图准备的额外托管分配中位数约由 25 MiB 降到 1192 字节，不包含相机已有像素缓冲、OpenCV 或 WPF 非托管位图内存。预览 P95 为 53.57 → 14.84 ms。全图 Blob 的总耗时仍在数百毫秒量级，主要受算法及机器负载影响；本轮不据此宣称 Blob 算法获得固定比例提速。输出尺寸与 Blob 前景像素面积 7068569 均一致。

完整样本、各阶段与程序集哈希见 [最终基准记录](../artifacts/tests/editor-performance/20261021-cache-preview-final/editor-performance.json)。这组数据不是屏幕显示总延迟，也不代表相机或产线的固定 FPS。

在没有其他大规模构建或性能测试运行时执行：

```powershell
./scripts/benchmark-editor.ps1 -Iterations 30
```

脚本使用隔离的构建输出和许可证测试目录，只导入已有 `artifacts/activation/current.vlic`，不调用签发器，不读取私钥，不连接真实相机。测试在同一个进程中预热后交替执行旧路径和实际生产缓存／位图路径，核对原始尺寸、像素和 Blob 面积。记录中位数、P95、各阶段耗时、托管分配及 DLL 哈希；不能将此合成测试直接换算为产线帧率。
